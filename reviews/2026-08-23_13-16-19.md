## Judge 1: Dr. Viktor — Embedded & Hardware

1. **[P0] Judge Dr. Viktor** — `src/hoverboard_control/EspCode/espcode/head_esp_code.ino:82-93,124-135`
The head firmware has no command watchdog, timeout, limit-switch handling, or explicit emergency-stop command from the manual UI.
Impact: one `Y`, `Z`, `U`, or `D` byte starts motion and it continues indefinitely until a different lowercase byte arrives; the UI's Hold button sends silence, which does nothing in this firmware.
Fix: add a non-blocking command deadline that calls `stopRotation()` and `dcBrake()` after a short timeout, add physical limit switches, and make the web/ROS contract send explicit stop bytes if that protocol is retained.

2. **[P0] Judge Dr. Viktor** — `src/hoverboard_control/EspCode/espcode/hoverboard_code.ino:186-203`
The ultrasonic implementation never waits for ECHO to rise and divides an already-centimetre conversion by 1000.
Impact: it usually reports a near-zero distance immediately after trigger; rear-safety telemetry is invalid, so the robot can reverse into an obstacle without a valid rear interlock.
Fix: implement a rising-edge then falling-edge state machine, compute `distance_cm = duration_us * 0.0343f / 2.0f` exactly once, publish invalid/timeout status explicitly, and fail safe on invalid measurements while reversing.

3. **[P1] Judge Dr. Viktor** — `src/hoverboard_control/EspCode/espcode/head_esp_code.ino:86-92`; `src/hoverboard_control/hoverboard_control/manual_controller.py:117-120`; `src/hoverboard_control/docs/aiSummary.md:14-18`
The head protocol has three incompatible definitions: firmware uses lowercase as stop/brake, Python accepts lowercase as normal movement, and documentation claims lowercase duplicates uppercase and silence stops.
Impact: a future caller can command motion where it expects braking, or wait for a timeout that firmware does not implement.
Fix: select one protocol, encode it as constants shared by ROS and firmware documentation, and reject unsupported command bytes.

4. **[P1] Judge Dr. Viktor** — `src/hoverboard_control/EspCode/espcode/head_esp_code.ino:21-25`
GPIO2 is a boot-strapping pin and is declared as a mandatory motor PWM output without an electrical startup-state specification.
Impact: attached motor-driver circuitry can prevent ESP8266 boot or produce unsafe output during reset.
Fix: document the external pull-up/down and driver enable state, validate cold-boot behavior on hardware, or move PWM/enable to a pin safe for the actual board and wiring.

## Judge 2: Elena — System Architecture

1. **[P0] Judge Elena** — `src/hoverboard_control/hoverboard_control/head_controller.py:22,109-113,122-144`; `src/hoverboard_control/EspCode/espcode/head_esp_code.ino:82-93`
`head_controller` hardcodes `/dev/ttyUSB2` and relies on silence to stop, while the committed firmware listens on the actual head path contract `/dev/ttyUSB1` and has no silence timeout.
Impact: face-tracking head control is dead on the documented hardware path; if its port is repaired, face-loss fails to stop motors.
Fix: delete this duplicate controller or rebuild it around the same parameterized head-driver abstraction and the actual stop semantics.

2. **[P1] Judge Elena** — `src/hoverboard_control/hoverboard_control/manual_controller.py:175-176,222-233`
The controller suppresses all sensor-read exceptions and claims to rate-limit base logs with `int(now.nanoseconds / 1e9) % 1 == 0`, a condition that is always true.
Impact: serial loss and parse failures disappear while the node floods logs at 10 Hz, burying actionable evidence during a safety incident.
Fix: catch `serial.SerialException` and decode errors separately, record health state and timestamps, reconnect deliberately, and use a real monotonic last-log timestamp.

3. **[P1] Judge Elena** — `src/hoverboard_control/hoverboard_control/manual_controller.py:20-21`; `src/hoverboard_control/hoverboard_control/fusion_controller.py:69-79`
The manual and autonomous stacks each open base serial independently, using incompatible discovery policies, while launch separation is enforced only by documentation.
Impact: starting both stacks creates a serial ownership race and conflicting commands to the same motor controller.
Fix: create one serial-driver node with a lock/lease, parameterize stable device paths, and make launch modes mutually exclusive through a single mode argument or lifecycle gate.

4. **[P1] Judge Elena** — `src/hoverboard_control/hoverboard_control/manual_controller.py:49-50,197-203`
Front depth value `0` and rear telemetry defaults are treated as benign rather than a failed safety sensor.
Impact: camera or ultrasonic failure removes the corresponding interlock without a fault state, warning, or deliberate operator acknowledgement.
Fix: track sensor freshness and validity, publish a safety fault state, and fail closed for motion directions that require unavailable sensing.

## Judge 3: Kai — UI & Frontend

1. **[P0] Judge Kai** — `src/hoverboard_control/hoverboard_control/manual_web_controller.py:51-53,77`; `src/hoverboard_control/EspCode/espcode/head_esp_code.ino:82-93`
The UI labels Hold as “silence=stop,” but it sends no request and the deployed head firmware requires lowercase stop/brake commands.
Impact: the primary stop control for a moving head is false; a user presses Hold and the motor continues moving.
Fix: expose explicit pan and tilt stop endpoints, send them on Hold, and align UI copy only after firmware watchdog behavior is implemented and tested.

2. **[P1] Judge Kai** — `src/hoverboard_control/hoverboard_control/manual_web_controller.py:61-62,101-107`
Base movement and emotion UI update status before checking the HTTP response, while their Flask routes return `{"ok": true}` even when `node` is unavailable or the command is rejected.
Impact: the operator receives false confirmation for commands that never reached ROS.
Fix: use the same response validation used by `sendHead`, return 503 when the ROS node is unavailable, return 400 for invalid commands, and display connection loss prominently.

3. **[P1] Judge Kai** — `src/hoverboard_control/hoverboard_control/web_controller.py:64-92`
The autonomous UI silently discards fetch failures for movement, pause, emotions, startup pause state, and mode polling.
Impact: network disconnect, port conflict, and server errors present as a functioning controller.
Fix: centralize request handling with timeouts, error state, retry policy, disabled controls, and a persistent offline banner.

4. **[P2] Judge Kai** — `src/hoverboard_control/hoverboard_control/manual_web_controller.py:13-81`
HTML, CSS, and JavaScript are embedded in a Python triple-quoted string with no browser test coverage or cache versioning.
Impact: UI changes are difficult to test, browser cache problems are opaque, and the source is hostile to safe maintenance.
Fix: move assets to versioned static files, add a lightweight browser/API test, and serve cache-control headers during development.

## Remediation Roadmap

### P0 — Critical Blockers
1. Add head firmware watchdog, deterministic stop protocol, limit switches, and an end-to-end stop test. Do not operate the head from the web UI before this exists.
2. Replace the invalid HC-SR04 state machine and fix its unit conversion. Test close obstacle, no echo, and disconnected sensor behavior. Fail closed for reverse when rear sensing is stale or invalid.
3. Remove or repair `head_controller.py`; it currently targets the wrong device and assumes stop behavior that does not exist.
4. Make the test gate pass and add behavioral safety tests. A red lint-only suite is not quality control.

### P1 — Architectural Deficiencies
1. Define one versioned base/head protocol specification; enforce it in firmware, ROS, UI, and documentation.
2. Consolidate serial ownership into a single parameterized driver and eliminate dual-stack contention.
3. Treat sensor freshness, decode failure, serial disconnection, and web-to-ROS delivery failure as explicit fault states.
4. Replace hardcoded `/dev/ttyUSB*`, `/dev/video*`, hotspot name, and source-tree paths with parameters and stable udev identities.
5. Make all Flask routes truthful and add an operator-visible offline/fault banner.
6. Correct package dependencies and choose a supported ROS/Ubuntu/Python target.

### P2 — Technical Debt & Polish
1. Split inline web assets into static files and test them.
2. Replace swallowed broad exceptions and log floods with structured diagnostics.
3. Repair or remove stale autonomous files and documentation.
4. Fix package metadata, code style failures, and invalid Markdown.
